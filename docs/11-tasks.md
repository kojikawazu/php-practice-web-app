- #48（laminas のレートリミット）DONE: #47 で両 Laravel に入れたレートリミットを laminas にも実装し、issue #68 を閉じた（issue #142）。**laminas にはフレームワークの支援が無い**ため、Laravel が `RateLimiter` ファサード 1 行で済ませている中身を全部自分で書くことになる。そこが本リポジトリの目的（同一題材を別スタックで読み比べる）に最も差分が出る題材だった。**設計は Laravel の構造に合わせて 2 層に割った**: `Service\AuthThrottle`（ポリシー = 何回・何で区切るか）と `Model\LoginAttemptTable`（保存）。Laravel が `RateLimiter`（ポリシー）とキャッシュ（保存）に分かれているのと同じ切り方にすることで、**フレームワークが隠している内訳がそのままクラスとして見える**状態にしている。保存先は `lam_login_attempts` テーブル。セッションは Cookie を捨てるだけで回避でき、`laminas-cache` は依存が増えるうえ掃除も自前になるため採らなかった。**laminas 側にだけ「期限切れの掃除」という関心事が現れる**（キャッシュと違い TTL が無い）。判定のついでに期間外の行を削除する形にしたのは、掃除を別経路（cron 等）に持たせると**それが止まったときに気づけない**ため。**最大の発見は E2E の実測から出た**: laminas のフル実行 1 回で IP キーに **15 秒で 33 件**積まれる（分換算 約 132 件/分）。#47 で決めた IP 上限 60 回/分は**単発では通るが連続実行で落ちる**（33 + 33 = 66）状態で、**上限が正当なピーク流量より低い**という構造的に薄い margin だった。実行時間が短いから通っていただけである。そこで **3 アプリすべての IP 上限を 120 回/分へ引き上げた**（laminas だけ変えると方針が揃わず、読み比べの差分が「手段」以外に増えてしまうため）。守りの主役は変わらず「ユーザー識別子 + IP で 5 回/分」で、IP 側は暴走した自動試行の頭打ちという位置づけ。**Psalm（errorLevel=1）とは 5 往復した**: 既存の同種コードは baseline に入っているが、`static-analysis.md` が「新規コードの指摘を baseline
