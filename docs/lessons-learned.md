## 2026-09-05 サイズ上限のために足したオプションが、SSRF 対策のピン留めを黙って無効化しかけた

### 概要

URL プレビューの本文サイズ上限（issue #88）を、HTTP クライアントの `stream => true`（本文の遅延受信）で実装しようとした。しかしこのオプションは Guzzle のハンドラ選択を cURL から `StreamHandler` へ切り替えるため、**`CURLOPT_RESOLVE` による接続先 IP のピン留め（DNS リバインディング対策）が無効になる**。テストは全件緑のままで、この劣化はどこにも現れなかった。PR を出す前に vendor のコードを読んで気づき、方針を `sink` 方式へ変更した。

### 詳細

- 何が起きたか: `stream => true` を追加した状態で fullstack のテスト・Pint・Larastan・markdown lint がすべて緑になり、そのまま PR を出せる状態だった。実装の妥当性を確認するため Guzzle のハンドラ選択を読んだところ、`Utils::chooseHandler()` の戻り値が `Proxy::wrapStreaming()` で包まれており、`stream` オプションが設定されたリクエストは cURL ハンドラを通らないことが分かった。cURL を通らなければ `CURLOPT_RESOLVE` は当然効かない。`allow_url_fopen` が Off の環境では `StreamHandler` がそもそも選ばれないため、**同じコードでも php.ini の設定次第でセキュリティ特性が変わる**状態でもあった。
- なぜ起きたか（根本原因）: 2 つのセキュリティ対策が**同じ層（HTTP クライアントの転送設定）で、互いに排他な手段**によって実現されていた。SSRF のピン留めは cURL 固有のオプション、転送の打ち切りは cURL を迂回するオプション。片方を足すともう片方が消える関係だったが、**その関係はどちらのテストにも現れない**。`Http::fake` はハンドラを通らないため、転送層の劣化は原理的に検出できない（実際、`stream => true` を外しても 21 件のテストは全部緑のままだった）。
- 教訓 / 次からどうする: **HTTP クライアントに「転送の仕方」を変えるオプション（`stream` / `sink` / `curl` / `proxy` 等）を足すときは、ライブラリ内部のハンドラ選択まで読んで、既存のオプションが同じ経路で効き続けるかを確認する。** ライブラリはオプションによって黙ってハンドラを切り替えることがある。そして**テストが緑であることを根拠にしない**。フェイクはハンドラを通らないので、転送層の性質は検証できない。加えて、**セキュリティ対策が特定の実装（cURL）に依存しているなら、その依存自体をドキュメントに書いておく**（書いていなければ、次に転送設定を触る人は同じ地雷を踏む）。
- 補足: 代替として採った `sink` 方式（上限に達したら短い書き込みを返し `CURLE_WRITE_ERROR` で転送を中断させる）も、**中断が起きる経路そのものは自動テストで確認できない**。テストで固定できるのは「sink が上限で短い値を返す」という契約までで、その契約が cURL に転送を中断させるという前提はドキュメントで担保するしかない。テストの限界を消せないなら、**限界を明記して残す**。
- 関連: issue #88 / [`docs/06-security-specification.md`](./06-security-specification.md)（「本文サイズ上限の効かせ方」に採用理由と限界を記載）/ [security.md](../.claude/rules/security.md)（多層防御: 1 層の漏れが即脆弱性にならないようにする）

## 2026-09-04 テストを増やした PR で、`docs/11` の件数だけ直して `docs/08` のケース一覧を更新し忘れた

### 概要

テストに関する記録の正本が `docs/08`（ケースの**内容**）と `docs/11`（ケースの**件数**）に粒度違いで 2 箇所あり、`docs/11` を更新した時点で「テストの記録は済んだ」と錯覚して `docs/08` を落とした。PR 作成前のセルフレビュー（チェック 4）で検出し、同一 PR 内で修正した。

### 詳細

- 何が起きたか: issue #74（laminas の監査列）の対応で単体 5 件・IT 2 件を追加した際、`docs/05`（監査列の設定責務）と `docs/11`（タスク一覧・進捗メモの件数 103 → 110）は更新したが、`docs/08` の laminas テストケース一覧表に監査列の行を足していなかった。main には入っていない。
- なぜ起きたか（根本原因）: [documentation.md](../.claude/rules/documentation.md) の影響マップを**主たる変更種別で 1 行だけ引いて終わらせた**。今回引いたのは「DB スキーマ・データフローの変更 → `docs/05`」で、同時に該当する「テスト戦略・ケース・品質目標の変更 → `docs/08`」を引かなかった。**バグ修正に付随するテスト追加を「テスト戦略の変更」と読まなかった**のが直接の原因。加えて `docs/11` の進捗メモ冒頭に「テスト規模（ケース数・正常/異常の比率）の正本はここに置く」と明記されているため、そこを直したことで記録が完了したと感じてしまった。**正本が粒度別に 2 箇所へ分かれているのに、片方から他方を思い出す手掛かりが無い**構造が効いている。
- 教訓 / 次からどうする: **テストを 1 件でも増減させた PR は、`docs/08`（ケース一覧）と `docs/11`（件数）を必ずセットで確認する。** 影響マップは 1 行引いて終わりにせず、**変更したファイルの種類から逆引きして 2 行目・3 行目が無いか見る**（今回なら `test/` 配下を触っている時点で `docs/08` が該当する）。ドキュメントの正本が粒度別に分かれている場合は、片方だけ更新して終われてしまう構造自体を疑う。
- 関連: issue #74 / [documentation.md](../.claude/rules/documentation.md)（影響マップ）/ [quality-gate.md](../.claude/rules/quality-gate.md)（セルフレビューで検出）/ `docs/08-test-specification.md` / `docs/11-tasks.md`

## 2026-09-03 `grep` を使った CI ガードが、検出 0 件の「正常系」で無言のまま落ちる

### 概要

秘匿ファイルの混入を検出する CI ジョブを、参考実装どおり `tracked=$(git ls-files | grep -E ... | grep -vE ...)` の形で書くと、**秘匿ファイルが 1 件も無い（＝望ましい）ときにジョブが終了コード 1 で失敗する**。しかもメッセージを 1 行も出さないため、失敗の理由が画面から読み取れない。実装前にローカルで再現して発覚した。

### 詳細

- 何が起きたか: issue #120 に載っていた実装案（他リポジトリでの実績あり）をローカルで実行したところ、混入 0 件の状態で終了コード 1・出力ゼロで終了した。CI に入れていれば、導入初日から赤いまま原因不明のジョブになっていた。
- なぜ起きたか（根本原因）: 3 つの仕様が噛み合った結果である。①`grep` は**マッチ 0 件でも終了コード 1** を返す（エラーではなく「見つからなかった」の意）②GitHub Actions の `run:` は `bash -e` で実行される ③`var=$(cmd)` という**単純な代入コマンドの終了コードは、コマンド置換の中身の終了コード**になる。よって「1 件も見つからない」が代入の失敗として扱われ、`set -e` がスクリプトを即終了させる。`||` や `if` の条件部に置かれた `grep` は `set -e` の対象外になるため、**同じ `grep` でも書く位置によって挙動が変わる**点が気づきにくさを生む。
- 教訓 / 次からどうする: **シェルで「0 件が正常」の検査を書くときは `grep` の終了コードに依存しない。** 出力の有無に関わらず 0 で終わる `awk` に置き換えるのが確実（`awk '$0 ~ ENVIRON["PAT"]'`）。`grep` を使うなら `|| true` ではなく終了コード 1 と 2 以上（正規表現エラー等＝ガードの故障）を区別して扱う。加えて、**参考実装は「動いた実績がある」ことを根拠に写さず、必ず手元で正常系・失敗系の両方を実行して終了コードまで確認する**。今回は正常系を実行しなかった場合に限って本番で初めて壊れる形だった。
- 補足: `awk` へパターンを渡すときは `-v` ではなく `ENVIRON` を使う。`-v` は値のエスケープを再解釈するため `\.` が `.` に化け、**リテラルのドットが任意 1 文字にマッチする別物の正規表現**になる（誤検知の方向に壊れるため、これも静かに間違える）。
- 関連: issue #120 / `.github/workflows/ci.yml` の `secret-scan` ジョブ / [github-actions.md](../.claude/rules/github-actions.md)（`run:` の中身を shellcheck に流す方針。ただし **shellcheck はこの終了コードの罠を検出しない**ため、実行して確かめるしかない）/ [testing.md](../.claude/rules/testing.md)（ガード自体をテストする）

## 2026-09-02 ルート直下に置いた設定ファイルが、CI で「コード変更」と判定される

### 概要

CI の `changes` ジョブは除外リスト方式（どの除外にも当たらない = コード変更）で fail-safe に倒してある。そのため**新しく追加した設定ファイルは、放っておくと必ず「コード変更」側に落ちる**。ツール設定を足した PR で PHP のテストが全部走り、**本来走るべき軽量チェックだけが走らない**という逆転が起きる。

### 詳細

- 何が起きたか: 同じ日に 2 回踏んだ。1 回目は `markdownlint-cli2` を devDependency 化した際のルート `package.json` / `package-lock.json`（issue #114）、2 回目は PR テンプレート用の入れ子設定 `.github/PULL_REQUEST_TEMPLATE/.markdownlint.jsonc`（issue #103）。どちらも実装直後のセルフレビューで気づいたため main には入っていない。
- なぜ起きたか（根本原因）: 除外リストは「既知の無関係ファイル」を列挙する形なので、**新しいファイルは定義上どれにも当たらない**。fail-safe としては正しい挙動（未知のものはテストを走らせる）だが、**同時に肯定リスト（`docs`）にも入っていない**ため、そのファイルを読む唯一のジョブ（`markdown-lint`）が起動しない。「安全側に倒れている」ように見えて、**検査が 1 つ欠落する**のがこの構造の盲点。
- 教訓 / 次からどうする: **リポジトリに新しい設定ファイル・マニフェストを追加したら、同じ PR で `changes` ジョブのフィルタを更新する。** 除外リスト（`test` / `lint` / `e2e`）と肯定リスト（`docs` / `workflows`）の**両方**を見る。判定は picomatch で実際に突き合わせて検証する（フィルタの誤りは「CI が緑のまま検査が減る」形でしか現れない）。
- 関連: [`.claude/rules/github-actions.md`](../.claude/rules/github-actions.md)（2 回起きたためルールへ昇格した）、issue #114 / PR #117、issue #103 / PR #121

## 2026-09-02 `new URL('localhost:8001')` は例外を投げず、ホスト名が空文字で通る

### 概要

E2E の接続先 allowlist ガードを実装した際、スキームを省いた URL が `new URL()` で**例外にならずに解釈され**、`hostname` が空文字のまま検査に流れた。ガード自体は fail-closed で止まったが、失敗メッセージが「許可されていないホスト: （空）」となり原因が読めなかった。

### 詳細

- 何が起きたか: `resolveUrl('E2E_FS_URL', 'localhost:8001', ...)` が「URL として解釈できない」ではなく「許可されていないホスト」で落ちた。ガードのテストが期待メッセージ不一致で失敗して発覚した。
- なぜ起きたか（根本原因）: `new URL('localhost:8001')` は **`protocol: 'localhost:'` / `hostname: ''` として成功する**（`localhost:` をスキームと解釈する）。URL の妥当性を「`new URL()` が例外を投げるか」だけで判定すると、この形が漏れる。
- 教訓 / 次からどうする: **URL の検証はスキームを先に検査する**（`http:` / `https:` のみ許可）。`new URL()` の成否だけを妥当性の判定に使わない。あわせて、**ガードは「止まること」だけでなく「メッセージが原因を指すこと」までテストする**（止まっても原因が読めなければ、次の人は環境変数を手で書き換えて回避しようとする）。
- 関連: [`.claude/rules/testing.md`](../.claude/rules/testing.md)「テスト対象・テスト DB の接続先（破壊防止）」、`e2e/helpers/config.ts`、issue #105 / PR #118

## 2026-08-23 `session_config` を足すと `session_storage` も必須になり、全リクエストが 500 になる

### 概要

laminas でセッション ID 再生成（セッション固定攻撃対策）を入れる際、`session_config` を追加したところ、`SessionManager` の生成が例外で失敗し、1 画面ではなく**全リクエスト**が 500 になった。

### 詳細

- 何が起きたか: `module.config.php` に `session_config` を追加した直後、アプリ全体が 500。`Module::onBootstrap` の CSRF リスナーが `SessionManager` を解決するため、**セッションを使わない画面まで巻き込まれる**。
- なぜ起きたか（根本原因）: `SessionManagerFactory` は `session_config` を見つけると、対になる **`session_storage` も必須で要求する**（欠けると `ServiceNotCreatedException`）。「設定を 1 つ足しただけ」に見えて、**ファクトリが要求する設定キーの組が変わる**のが原因。
- 教訓 / 次からどうする: **Laminas でコンテナ経由の設定キーを足すときは、そのファクトリが連鎖して要求する他のキーを先に確認する**（`SessionManagerFactory` なら `session_config` + `session_storage` の対）。ブートストラップで解決されるサービスは影響範囲が全リクエストに及ぶため、追加後は必ず 1 画面ではなく**トップページと認証不要画面の両方**で疎通を確認する。
- 関連: `apps/laminas/module/Application/config/module.config.php`（理由をコメントで記録済み）、[`.claude/rules/php.md`](../.claude/rules/php.md)「DI」、issue #85 / PR #101

## 2026-07-25 `dorny/paths-filter` の否定パターンは、既定の OR 評価で互いを打ち消す

### 概要

CI のパスフィルタを「除外リスト方式」で書いたが、否定パターンを並べただけでは**除外が一切効かず、常に true**になっていた。「ドキュメントだけの変更でテストが走らない」はずが、全部走っていた。

### 詳細

- 何が起きたか: `- '!docs/**'` `- '!**/*.md'` のように否定パターンを並べたフィルタが、md だけの変更でも `true` を返した。`'**'` + `'!docs/**'`（全部 + 除外）の形も同様に効かない。
- なぜ起きたか（根本原因）: `dorny/paths-filter` は**パターンごとに picomatch を評価し、既定では結果を OR（`some`）で束ねる**。`docs/x.md` は `'!docs/**'` には一致しないが `'!**/*.md'`… のような別の否定パターンには一致するため、**どれか 1 つでも真になれば全体が真**になる。否定を並べるほど真になりやすい。
- 教訓 / 次からどうする: **除外リストを書くときは `predicate-quantifier: every`（AND 評価）を指定し、否定パターンだけを並べる**（「どの除外にも当たらない = コード変更」の意味になる）。肯定形のフィルタは `every` だと壊れるので**別ステップに分ける**。そして**フィルタを変更したら判定を実測する**（対象ファイル名を並べて期待値と突き合わせる）。誤りは「テストが黙ってスキップされる／無関係なジョブが走る」形でしか現れず、CI は緑のままになる。
- 関連: [`.claude/rules/github-actions.md`](../.claude/rules/github-actions.md)「パスフィルタの実装（重要な落とし穴）」、`docs/09-architecture-specification.md`、PR #65
