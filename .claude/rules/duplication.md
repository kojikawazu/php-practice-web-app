# 重複と共通化

**重複は「同じコードが 2 つある」ことではなく、「同じ知識が 2 箇所にある」こと。** 片方を直したらもう片方も必ず直さねばならない関係にあるものだけが、共通化すべき重複である。

## 共通化する / しないの判断

| 状況 | 判断 |
| --- | --- |
| 同じ**業務ルール・仕様**が複数箇所にある（税率計算、ステータス遷移条件、権限判定） | **共通化する**。仕様変更時の直し漏れが即バグになる |
| 同じ**リテラル値**が複数箇所にある（上限値・API パス・キー名） | **定数化して共有する**。置き場所は下記「共通化するときの置き場所」に従う（命名は [coding-standards.md](./coding-standards.md) の UPPER_SNAKE_CASE） |
| 同じ**検証内容**が複数レイヤにある | **共通化する**。担当レイヤを 1 つに決める（Laravel = コントローラの `validate()` / Laminas = `src/InputFilter/`。[php.md](./php.md) に従い、同じ検証を複数レイヤに二重定義しない） |
| 形は同じだが**変わる理由が違う**（偶然の一致） | **共通化しない**。片方だけ変更したい日が必ず来る |
| **信頼境界をまたぐ**（フロントとバックエンドの入力検証） | **重複させる**。ただし定数・スキーマは共有できるなら共有する |
| **層をまたぐ型**（DTO とドメインモデル、DTO と DB エンティティ） | **共通化しない**。似ていても変更理由が違う（API 契約 / 業務 / 永続化）。共通化すると内部スキーマが API に漏れる |
| テストの**期待値・ケース内容** | **共通化しない**。テストは重複してでも読んで分かることを優先する（セットアップの共通化は可） |

## 早すぎる共通化をしない

- **2 回目までは重複を許容し、3 回目で共通化する**。2 箇所では「同じ知識」なのか「たまたま同じ形」なのか判別できない。
- 共通化した結果 **`if` / フラグ引数で分岐が増えるなら、それは共通化すべきでなかった**サイン。分けて書き直す。
- 「将来使うかもしれない」ための抽象化を作らない。**今 3 箇所で使われている事実**だけを根拠にする。
- 判断に迷ったら**重複を残す**。重複は後から共通化できるが、間違った共通化を剥がすのは高くつく。

## 共通化するときの置き場所

- 置き場所は**参照範囲**で決める（型・定数と同じ判断軸）。1 箇所に閉じるならその場、モジュール内なら当該モジュール、複数モジュールから参照されるなら共有層へ。
- **`common` / `util` / `helper` を「とりあえずの置き場」にしない**。無関係な処理の集積になり、全モジュールがそこへ依存して**レイヤの一方向依存が壊れる**。名前が付けられない＝共通化の単位が間違っている。
- 共通化した先が上位レイヤになってはならない。**共通化は必ず下位（または同位の共有層）へ抽出**する。

## レビュー観点

- コピー＆ペーストの痕跡（同じ条件式・同じマジックナンバー・同じ変換処理）が 3 箇所以上にないか。
- 逆に、**共通化されたものにフラグ引数や分岐が増え続けていないか**（過剰共通化の兆候）。
- 共通化の置き場が `common` / `util` に流れ込んでいないか。

## 本プロジェクト固有の注意（3 アプリ構成）

- `apps/laravel-fullstack` / `apps/laravel-api` / `apps/laminas` は**同一題材を別スタックで実装して読み比べる**ことが目的である。3 アプリ間で処理が似ていても、**アプリをまたぐ共通化はしない**（学習目的とスタック差分の可視化を壊すため）。
- 共通化の検討はあくまで**同一アプリ内**で行う。3 アプリ共通の取り決めはコードではなく `docs/` の仕様書と `.claude/rules/` で表現する。
